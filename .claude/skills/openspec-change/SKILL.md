# OpenSpec: Creating a Change

OpenSpec splits work into three stages: **create a change** → implement it → archive it. This skill covers only the first stage, which is where nearly all the value and nearly all the mistakes live. A change proposal that is precise costs an hour; one that is vague costs a week of rework.

The core discipline: **no implementation code until the change is written, validated, and approved.** If you find yourself editing source files during this skill, stop — you've skipped a stage.

## Step 0: Orient before writing anything

Three reads, in this order. Do not skip them — guessing at repo conventions is the most common way these proposals go wrong.

1. **`openspec/AGENTS.md`** — generated by `openspec init` and authoritative for the installed version. Where it contradicts this skill, AGENTS.md wins; OpenSpec's conventions shift between releases and this skill may be behind.
2. **`openspec/project.md`** — the project's tech stack, conventions, and naming rules.
3. **Existing state** — what's already built and what's already in flight:

```bash
openspec list           # active changes — check for overlap before proposing
openspec list --specs   # existing capabilities
openspec show <spec>    # read any spec you're about to modify
```

If `openspec --help` shows commands or flags that differ from the above, trust the CLI over this skill.

Two things to notice while orienting:

- **An existing change already covers this.** Extend it instead of creating a competing one. Two changes touching the same requirement will conflict at implementation time.
- **A spec you're about to modify doesn't exist yet.** Then this is an `## ADDED Requirements` change against a new capability, not a `## MODIFIED` one.

## Step 1: Decide whether a change is warranted

Changes exist to capture decisions about **behavior**. They are overhead when there is no decision to record.

| Write a change | Skip the change |
|---|---|
| New feature or capability | Typo, comment, formatting |
| Behavior of existing feature changes | Pure refactor with identical behavior |
| Breaking change to an API or contract | Dependency bump with no behavior change |
| Bug fix where correct behavior is disputed or unspecified | Bug fix restoring behavior the spec already mandates |
| Architecture or data-model decision | Adding a test for already-specified behavior |

When it's genuinely ambiguous, ask the user rather than guessing — a spurious change wastes their review time, and a missing one loses the decision.

## Step 2: Name the change

Change IDs are kebab-case and verb-led. The verb signals intent at a glance in `openspec list`:

- `add-two-factor-auth`
- `update-invoice-tax-rounding`
- `remove-legacy-soap-endpoint`
- `refactor-order-pipeline`

Keep it specific enough to be unambiguous a month later. `fix-bug` and `update-api` are useless in a list of twenty changes.

## Step 3: Scaffold the directory

```
openspec/changes/{change-id}/
├── proposal.md                      # why, what, impact
├── tasks.md                         # ordered implementation checklist
├── design.md                        # OPTIONAL — only for non-obvious decisions
└── specs/
    └── {capability}/
        └── spec.md                  # the delta — see Step 5
```

`scripts/scaffold_change.sh` creates this with stub content:

```bash
./scripts/scaffold_change.sh add-two-factor-auth auth
```

Include `design.md` only when there's a real decision to record — a technology choice, a tradeoff between two viable architectures, a migration strategy. For a straightforward change it's noise, and reviewers learn to skim files that are usually empty.

## Step 4: Write proposal.md

Keep it short. Reviewers read this to decide *whether* to approve; the specs tell them *what* they're approving.

```markdown
## Why

[1–3 sentences. The problem or the driver. Not the solution.]

## What Changes

- [Bullet per user-visible change]
- [Group related bullets if there are many]
- **BREAKING**: [Prefix anything that breaks an existing contract]

## Impact

- **Affected specs**: auth, session
- **Affected code**: `src/auth/`, `src/middleware/session.ts`
- **Migration**: [Required steps, or "none"]
```

Two failure modes to avoid:

- **"Why" that restates "What."** "Why: we need to add 2FA" is not a reason. "Why: account takeovers rose 40% last quarter and password-only auth can't mitigate credential stuffing" is.
- **Unmarked breaking changes.** If any existing caller, integration, or stored record has to change, mark it `**BREAKING**`. Reviewers scan for that token; burying it in prose means it gets approved unnoticed.

## Step 5: Write the spec deltas

This is the part that fails validation. The full syntax reference, including every operation and the exact validation rules, is in **`references/delta-format.md`** — read it before writing your first delta, and re-read it if `--strict` rejects your change.

The essentials:

Deltas live at `openspec/changes/{change-id}/specs/{capability}/spec.md` and contain **only what changes**, never the whole spec. Group requirements under an operation header:

```markdown
## ADDED Requirements

### Requirement: Two-Factor Authentication

The system SHALL require a second authentication factor for accounts with 2FA enabled.

#### Scenario: Valid TOTP code

- **WHEN** a user with 2FA enabled submits a valid TOTP code within its time window
- **THEN** the system issues a session token

#### Scenario: Expired TOTP code

- **WHEN** a user submits a TOTP code outside its validity window
- **THEN** the system rejects the attempt and does not issue a session token
```

Four rules that account for most `--strict` failures:

1. **Header levels are load-bearing.** `## ADDED Requirements` (h2) → `### Requirement: Name` (h3) → `#### Scenario: Name` (h4). One wrong `#` and the parser won't see the block.
2. **Every requirement needs at least one scenario.** A requirement with no `#### Scenario:` fails validation. This isn't bureaucracy — a requirement you can't write a scenario for is one you haven't specified precisely enough to implement or test.
3. **`## MODIFIED Requirements` needs the complete replacement text**, header and all scenarios, not a diff of the changed lines. The delta replaces the requirement wholesale.
4. **`SHALL` for normative behavior.** Reserve `SHOULD` for genuine recommendations and `MAY` for optional behavior. Mixing these up makes requirements untestable.

## Step 6: Write tasks.md

Numbered sections, checkbox items, ordered so that each is verifiable when checked off:

```markdown
## 1. Data model

- [ ] 1.1 Add `totp_secret` and `totp_enabled` columns to users table
- [ ] 1.2 Write migration with rollback

## 2. Backend

- [ ] 2.1 Implement TOTP generation and verification
- [ ] 2.2 Add enrollment endpoint
- [ ] 2.3 Gate login flow on `totp_enabled`

## 3. Verification

- [ ] 3.1 Unit tests covering each scenario in the spec delta
- [ ] 3.2 Manual check: enrollment, valid code, expired code
```

Order by dependency, not by convenience. If task 2.3 can't be done before 1.1, it belongs after it. And every scenario in the delta should be traceable to something in this list — a scenario nobody implements is a spec that lies.

## Step 7: Validate

```bash
openspec validate {change-id} --strict
```

Use `--strict`. Non-strict validation passes things that will bite later. Also worth a look:

```bash
openspec show {change-id}    # renders as reviewers will see it
openspec diff {change-id}    # spec before/after
```

Fix every error before moving on. If a message is opaque, `references/delta-format.md` maps the common ones to their causes.

## Step 8: Stop and get approval

Validation passing is not approval. Present the change to the user and wait:

> Created `add-two-factor-auth` — validates clean under `--strict`.
>
> - **Proposal**: TOTP second factor, opt-in per account
> - **Spec deltas**: `auth` (3 added requirements), `session` (1 modified)
> - **Tasks**: 8 across data model, backend, verification
> - **Breaking**: none
>
> Anything to adjust before I start implementing?

Then stop. Do not begin implementation in the same turn — the review is the point of the whole exercise, and implementing pre-emptively means any correction is now a correction to code as well as to the spec.

## Common failure modes

| Symptom | Cause | Fix |
|---|---|---|
| `--strict` reports no requirements found | Wrong header level, or missing `## ADDED Requirements` group header | Check `#` counts against Step 5 |
| Requirement rejected as incomplete | No `#### Scenario:` under it | Add at least one scenario |
| MODIFIED requirement loses content after archive | Delta contained only changed lines | Include the complete replacement requirement |
| Two changes conflict at implementation time | Didn't run `openspec list` first | Check active changes before proposing |
| Reviewer approves a breaking change unnoticed | `**BREAKING**` marker missing | Mark it in "What Changes" |
| Change is enormous and stalls in review | Multiple unrelated concerns in one change | Split into separate changes, one decision each |

## Scope boundary

This skill ends at approval. Implementation (working through `tasks.md`, checking items off as they land) and archiving (`openspec archive {change-id}` once deployed) are separate stages with different concerns. Don't fold them in here.
