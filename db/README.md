# Database

MySQL 8.0. Migrations are generated by `drizzle-kit` from `packages/db/src/schema` and land in
`migrations/` as plain SQL.

## Access control

There is no MySQL equivalent of Postgres Row Level Security. The API's connection uses a
least-privilege credential instead: `SELECT, INSERT, UPDATE, DELETE` on the application database,
and nothing else — no `CREATE`, `ALTER`, `DROP`, or grant-management privilege. Migrations run
under a separate credential that holds full DDL. This is what
`openspec/changes/migrate-postgres-to-mysql/design.md` ("Row Level Security is deleted, not
emulated") replaces RLS's default-deny posture with: a compromised or misused API connection can
still read and write every row (there is only one writer, and RLS's own job in the Postgres setup
was defending against a hypothetical *second* one — see `docs/ARCHITECTURE.md` §2), but it cannot
alter the schema, create a new table, or grant itself more.

`docker-compose.yml` creates both credentials on first start: `siders_migrate` (via the standard
`MYSQL_USER`/`MYSQL_PASSWORD` image variables, full privileges on `siders`) and `siders_api` (via
`db/init/01-create-api-user.sh`, DML only, password overridable via `MYSQL_API_PASSWORD` the same
way the other two credentials are). Point `DATABASE_URL` at `siders_api` for the running API and
at `siders_migrate` for `drizzle-kit generate`/`migrate`.

`siders_api`'s grant is issued to `'siders_api'@'%'` (any host), not scoped to a specific
container subnet: this compose file defines no `api` service — the API runs outside it, reaching
MySQL through the published `3306:3306` port, so there is no fixed container IP or CIDR to scope
the grant to. In an environment that also firewalls or network-isolates MySQL, that boundary is
what actually restricts who can reach the port at all; this credential's own privileges (DML
only, no DDL) are the second layer regardless of who connects.

## Migrations

- `migrations/` holds one baseline (`0000_...sql`, generated from the schema) plus
  `0001_seed_permission_catalog.sql` (the fixed permission catalog, the Owner role, and the
  sub-brand catalog — seeded in a migration, not in `seed.sql`, because production needs it too).
- Generate a new migration after a schema change: `pnpm --filter @siders/db db:generate`.
- Apply migrations: `pnpm --filter @siders/db db:migrate` (uses `DATABASE_URL`).
- `seed.sql` is local-dev only — it seeds the first Owner *user*, not the catalog. Load it
  directly against your local database after migrating.
