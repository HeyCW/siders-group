## Context

Per `docs/ARCHITECTURE.md` §5.3/§5.5: two tokens in httpOnly cookies (`sid_at`, 15 minutes; `sid_rt`, 30 days sliding), a script-readable `csrf_token` double-submit cookie, and a two-tier check — identification is stateless and never rejects, authorization is stateful and fails closed. All of that is implemented and specified (`specs/authentication`, `specs/authorization`). Nothing in `apps/admin` uses any of it: `apps/admin/src/App.tsx:14-16` is a stub and every route is unguarded.

The five endpoints this change builds against are existing and are not redesigned:

```
POST /auth/staff/login   apps/api/src/modules/auth/auth.routes.ts:110   requirePublic(), rate-limited, 204 + cookies, no body
GET  /users/me           apps/api/src/modules/users/user.routes.ts:17   requireStaff({ allowPendingPasswordChange: true })
POST /staff/me/password  apps/api/src/modules/staff/staff.routes.ts:67  requireStaff({ allowPendingPasswordChange: true }), rate-limited
POST /auth/refresh       apps/api/src/modules/auth/auth.routes.ts:84    requirePublic(), rate-limited, 204 + rotated cookies
POST /auth/logout        apps/api/src/modules/auth/auth.routes.ts:90    requirePublic(), 204, clears cookies
```

Two defects surfaced while designing the client against these:

1. **CSRF cookie has no lifetime.** `setCsrfCookie` (`apps/api/src/lib/csrf.ts`) sets neither `maxAge` nor `expires`, so browsers treat it as a session cookie. `sid_rt` carries `maxAge: 30 * 24 * 60 * 60 * 1000` (`apps/api/src/lib/cookies.ts`). After a browser restart the jar can hold `sid_rt` with no `csrf_token`. `createCsrfMiddleware` is mounted globally at `apps/api/src/server.ts:48`, before every route, and fires whenever `sid_at || sid_rt` is present — so sign-in, refresh, and logout all 403 `csrf_failed` until `sid_rt` itself expires (up to 30 days) or the jar is cleared by hand. The `maxAge` fix below (Decisions) stops this from happening again; it does nothing for a caller already caught in it, which is exactly why the CSRF re-pairing endpoint exists.
2. **No refresh call anywhere in `apps/admin`.** `apps/admin/src/lib/api.ts` never touches `/auth/refresh`. An expired access credential is anonymous to `authenticate` (per `specs/authentication`), so `requireStaff`/`requirePermission` then throw 403 `forbidden`. A valid 30-day session is bounced to sign-in after 15 idle minutes.

`resolveStaffAccess` (`apps/api/src/middleware/authorize.ts:136-161`) already computes `permissionKeys` and the Owner comparison on every gated request; today only `requireStaff`/`requirePermission` consume the result (into `req.staffRole: { roleId, isOwner }`, `authorize.ts:127-133, 196-197, 228-233`), and `GET /users/me`'s own DTO (`user.mapper.ts`) is built from a separate, narrower query in `user.repository.ts` that never touches `role_permissions`.

This change follows the app's actual established frontend pattern — a plain `apiFetch`/`apiUpload` wrapper (`apps/admin/src/lib/api.ts`) plus local hooks (`useAsyncAction.ts`) — rather than `docs/ARCHITECTURE.md` §8.2's aspirational TanStack Query / react-hook-form, which no admin screen currently uses.

## Goals / Non-Goals

**Goals:**
- Make a staff session survive the two conditions every real session hits: a browser restart inside the 30-day refresh window, and 15 idle minutes inside a signed-in day.
- Make the 403-is-ambiguous problem a specified algorithm, not a per-screen guess, and make single-flight refresh a first-class requirement rather than an implementation footnote — a naive interceptor here doesn't degrade, it destroys the session it was trying to save.
- Give a caller already caught by the pre-fix CSRF lockout (a live `sid_rt`, no `csrf_token`) a way back in that keeps them signed in — the `maxAge` fix alone only prevents new occurrences, it cannot repair one already in effect.
- Let the admin app render permission-aware navigation without moving one bit of enforcement to the client.
- Land the CSRF fix generally enough that it also fixes the reader flow for free, since both share `setCsrfCookie`.

**Non-Goals:** see `proposal.md` - Non-Goals. Additionally, at the design level: no state-management library beyond what `apps/admin` already uses (no TanStack Query, no Redux/Zustand); no visual design system work beyond what's needed to exercise the state machine below; no change to `resolveRedirectTarget` (`apps/api/src/lib/redirect.ts`), which stays exactly what it is today — a server-side, Google-flow-only helper that this change does not call, since staff sign-in returns 204 with no redirect semantics.

## Decisions

**CSRF cookie lifetime tracks the refresh cookie's, via a shared constant.** `setCsrfCookie`'s options type is currently `Pick<CookieOptions, 'secure' | 'domain'>` (`csrf.ts:61-64`) — no `maxAge` parameter exists to set. The fix: export `REFRESH_TOKEN_MAX_AGE_MS` from `cookies.ts` (currently a private `const`), extend `setCsrfCookie` to accept and apply a `maxAge` of at least that value, and pass it from all three call sites that currently call `setCsrfCookie(res, issued.csrfToken, sharedCookieOptions(env))`: staff login (`auth.routes.ts:120`), refresh (`auth.controller.ts:26`), and the Google callback (`google.routes.ts:114`).
- Alternative considered: give the CSRF cookie its own independent, shorter lifetime (e.g. 7 days) on the theory that a shorter-lived script-readable cookie is marginally safer. Rejected — a CSRF cookie that can expire before its refresh cookie reintroduces exactly the lockout this change exists to close, just on a longer timer instead of a browser restart. The cookie's job is to always be present whenever `sid_rt` is, so its lifetime has no independent value to tune.
- Because `setCsrfCookie` is subject-type-agnostic and is already called identically for the Google reader callback, this one fix closes the lockout for both audiences without any reader-specific change — consistent with the accepted "share one cookie" constraint below.

**A safe-method endpoint re-pairs a CSRF cookie for a caller already locked out.** The `maxAge` fix above stops *new* lockouts; it does nothing for a browser that already holds `sid_rt` with no `csrf_token`, and that state is otherwise a dead end for staff — every recovery route is a POST behind the very check stopping them:

```
POST /auth/staff/login  → 403 csrf_failed
POST /auth/refresh      → 403 csrf_failed
POST /auth/logout       → 403 csrf_failed   ← even the escape hatch is walled off
```

Readers don't have this problem. `GET /auth/google` → `GET /auth/google/callback` are both safe methods; `createCsrfMiddleware` returns before its check ever runs for `SAFE_METHODS`, and the callback already calls `setCsrfCookie` (`google.routes.ts:114`) — so a reader who hits this state just clicks sign-in again and is repaired incidentally, without anyone having designed for it. Staff have no equivalent GET in their sign-in path, which is the whole reason this needs its own mechanism.

The fix: a new `GET /auth/csrf`, named and mounted alongside `/auth/refresh`, `/auth/logout`, and `/auth/me` in `auth.routes.ts`, declared `requirePublic()` and rate-limited the same way `/auth/refresh` is. Because it is a GET, `createCsrfMiddleware` never reaches its check for this route at all — no carve-out of the fail-closed CSRF requirement is needed, unlike either alternative considered below.

Binding resolves in two steps, in this order, and both are necessary:
1. If `authenticate` has already populated `req.auth` (a cryptographically valid `sid_at`), bind the new token to `req.auth.sessionId`.
2. Otherwise, resolve `sid_rt` the same way `auth.service.ts`'s `refresh()` looks up a refresh credential, and bind to that session only if it is still unrevoked and unexpired; otherwise issue nothing.

Both steps matter, not just the second. `sid_at` is itself a *persistent* cookie (`maxAge: 15 * 60 * 1000`), while `csrf_token` was a session cookie before this change — a restart inside that 15-minute window leaves a valid `sid_at` with no CSRF cookie at all. Unlike the `sid_rt`-only case, `createCsrfMiddleware`'s binding check (`payload.sessionId !== req.auth.sessionId`) *is* enforced whenever `req.auth` is set, so a token bound only via the `sid_rt` path would come back mismatched the instant that same browser's next request also carries a live `sid_at`. Both resolution steps, checked in this order, are required for the mechanism to actually repair both windows it exists for.

The token is set as a cookie, never returned in the response body — the same as every other CSRF issuance. Returning it in JSON would make CORS, not same-origin cookie scoping, the thing standing between the token and a cross-origin reader, which is a strictly weaker guarantee than the double-submit pattern already relies on; the client reads it same-origin exactly as `csrfHeader()` in `apps/admin/src/lib/api.ts` already does for every other issuance. The response is uniform (204, always) regardless of which binding branch fired or whether one fired at all, so the endpoint cannot be probed to learn whether a given browser holds a live session.

This is explicitly **not** a refresh: no credential is rotated, no `app.sessions` row is created, no expiry is extended, and no revocation is lifted. It answers exactly one question — "what session, if any, do these cookies already identify?" — and re-issues the one artifact that was missing. A session that is revoked or already expired is no better off after calling it than before: every other check downstream still evaluates that session exactly as it would have anyway.

*Not a new attack surface, but one honest pre-existing property worth naming.* A hostile page can cause a victim's browser to issue this GET (an `<img>` tag is enough) but cannot read the resulting `Set-Cookie` cross-origin, so it still cannot produce the header half of the double-submit pair — the endpoint gives an attacker nothing they didn't already have. Separately, and neither introduced nor worsened by this change: `csrf_token` is `httpOnly: false` on `domain: COOKIE_DOMAIN` today, so any sibling subdomain under that shared domain could already read it, with or without this endpoint. That is a pre-existing property of the double-submit design this change inherits, not a consequence of the bootstrap mechanism, and closing it is explicitly out of scope here.

That forced GET is nonetheless chargeable, and that has to be accounted for separately from what it cannot read. Rate limiting reserves its bucket slot before the handler runs, and a forced GET that yields no token still reserves one — `sameSite: 'lax'` keeps it credential-less, not free. Keying the limiter on source IP the way `refreshRateLimiter` does (task 2.1) has two consequences worth naming rather than inheriting silently: a hostile page can spend a victim's own recovery budget on requests that accomplish nothing else, and — with no attacker at all — every staff member behind one office NAT hits the pre-fix lockout on the same Monday-morning restart and collectively spends one shared IP-keyed budget recovering from it, which is exactly the population this endpoint exists to serve. Both are denial of the recovery path, not a credential or privilege gain, and both are avoided the same way: key the limiter on the presented refresh credential (e.g. a hash of `sid_rt`) where one is present, so one caller's attempts cannot spend another's budget, and fall back to an IP-keyed cap only as a coarse flood guard for callers presenting no credential at all.

- Alternative considered: exempt `POST /auth/staff/login` from the CSRF check. Rejected — `createCsrfMiddleware` is deliberately fail-closed and applies uniformly to every state-changing request carrying a session credential (`specs/authentication` - "State-changing requests require a CSRF token"); carving out one route makes the fail-closed guarantee no longer really fail-closed, and it still leaves `/auth/refresh` and `/auth/logout` bricked for the same caller — sign-in is not the only wall they hit.
- Alternative considered: exempt `POST /auth/logout` as a universal escape hatch, so a locked-out caller can at least clear their state and start over. Weighed seriously — logout is arguably the lowest-severity route to exempt, since it only ever ends the caller's own session. Rejected anyway: it heals the lockout by destroying the session rather than preserving it, which is strictly worse for the caller than a mechanism that gets them back to work still signed in, and it still leaves a caller who wanted to *refresh* with nothing. The bootstrap endpoint subsumes it: once `/auth/csrf` has repaired the cookie, ordinary logout already works with no exemption needed.

**`GET /users/me` sources `permissionKeys`/`isOwner` from `req.staffRole`, not a second query.** `resolveStaffAccess` already resolves both on every gated request. The chosen shape: extend `StaffRoleContext` (`authorize.ts:10-13`) with `permissionKeys: string[]`, populate it in both `requireStaff` and `requirePermission` from the `access` value each already computes, and have `user.controller.ts`'s `getMe` read `req.staffRole.permissionKeys` / `.isOwner` instead of `user.service.ts`/`user.repository.ts` issuing an independent `role_permissions` join.
- Alternative considered: have `user.repository.ts`'s `findById` join `role_permissions`/`permissions` itself and compare against the Owner role id directly. Rejected as a second, redundant computation of exactly what the middleware already resolved one line earlier in the same request, and a second place that could drift from `resolveStaffAccess`'s definition of "effective permission."
- This is additive to `StaffUserDto`: `roleId`, `roleName`, `status`, `mustChangePassword`, and every other existing field are untouched, so nothing that already reads this DTO can break.

**Single-flight refresh: exactly one in-flight `/auth/refresh` call per session, ever.** The recovery path for a 403 on a feature request:

```
403 on a feature route (not the sign-in screen's own submission)
  └─▶ single-flight POST /auth/refresh
        ├─ succeeds ─▶ retry the original request once
        │                 └─ still 403 ─▶ re-probe GET /users/me
        │                                   ├─ probe ok   ─▶ permission denial → forbidden UI, stay signed in
        │                                   └─ probe fails ─▶ session gone → /login
        └─ fails ─▶ /login
```

"Single-flight" is load-bearing, not a nice-to-have: `specs/authentication` requires that reusing an already-rotated refresh credential "revokes every session in that credential's lineage." If N concurrent requests each discover their own 403 and each fire an independent refresh, the first rotates the credential and every other presents one already consumed — the backend cannot tell that from theft, so it revokes the whole lineage and hard-logs-out a caller who did nothing wrong. A correct interceptor therefore holds one shared in-flight refresh (e.g. one stored promise, created by whichever request discovers the 403 first and cleared when it settles) that every other discovering request awaits instead of duplicating.
- Alternative considered: retry each failing request independently with backoff, no de-duplication. Rejected — it is the exact failure mode above; backoff changes timing, not the fact that a second request will still present an already-rotated credential.
- Alternative considered: a proactive timer that refreshes shortly before the 15-minute mark (e.g. at 14 minutes) instead of reacting to a 403. Considered as a possible future latency optimization, not built here: a backgrounded or sleeping tab (laptop lid closed) sleeps through the timer just as easily as it would sit idle, so the reactive 403-triggered path is required regardless of whether a timer also exists. Adding one is a strict addition on top of this change's mechanism, not a substitute for it, so it's left as a follow-up rather than bundled in.
- The sign-in screen's own credential submission is explicitly excluded from this interceptor. It is the one screen where a 403 can occur with no session at all to refresh — for a returning caller whose `sid_rt` is still present but whose CSRF cookie was still missing before the fix above, the login POST itself would 403 `csrf_failed`, and attempting a refresh in response would be both meaningless (refresh cannot fix a CSRF mismatch) and itself blocked by the same missing cookie.

**A still-403 retry is disambiguated by re-probing, not by inspecting the status code.** `requireStaff` and `requirePermission` both throw 403 `forbidden` for "no staff session" (`authorize.ts:186-191`, `:218-223`), and `requirePermission` reuses the identical 403 `forbidden` for "insufficient permission" (`authorize.ts:230-232`). No staff session also yields 403, not 401 — unlike the reader side (`requireReader` throws 401 `unauthenticated`, `authorize.ts:110-114`), so a guard watching for 401 on the admin side never fires. After a refresh succeeds and the retried request still fails, the only way to tell "your role lacks this permission" from "your session is actually gone" apart is to ask a question only a real session can answer: `GET /users/me`. A successful probe proves a session exists (permission denial); a failed probe proves it doesn't (session gone).
- Alternative considered: add a new, more specific error code to `requirePermission` distinguishing "no session" from "insufficient permission." Rejected — it would touch an existing, working backend endpoint's error contract for a distinction the client can already recover with one extra request on what is already the uncommon path (reached only when refresh didn't resolve things), and this change's scope is additive to the backend, not a redesign of it.

**The interceptor branches on the CSRF error code before choosing a recovery path.** `createCsrfMiddleware` and `requireStaff`/`requirePermission` both answer 403, but for unrelated reasons and with different codes (`csrf_failed` vs `forbidden`), and only one recovery fixes either: refreshing cannot repair a CSRF mismatch, since the credential was never the problem, and bootstrapping cannot fix an authorization decision, since it never touches `req.staffRole`. The interceptor reads `code` before doing anything, and the two paths stay structurally separate rather than merging into one generic "on any 403, try everything" handler — a merged handler either tries both (risking the unbounded-chain problem below) or picks one arbitrarily, leaving the other failure mode unrecovered.
- **A third code, `password_change_required`, takes neither recovery path.** `requireStaff` and `requirePermission` also answer 403 coded `password_change_required` (`authorize.ts:193-194, 225-226`) when the caller's account has a pending change — distinct from both `forbidden` and `csrf_failed`, and neither refresh nor bootstrap addresses it, since the session is valid and the CSRF pairing is intact; only the change screen resolves it. The interceptor's three-way branch treats it as its own case: re-resolve session state and enter the forced password-change screen, attempting neither other recovery. Reachability is narrow — an admin-triggered reset revokes the target's sessions, so the flag cannot flip under a session already past this check — but the interceptor is specified as *the* 403-disambiguation algorithm, so the third code it can actually receive belongs in it rather than falling through to the generic "treat a 403 as authoritative" rule and rendering as a permission denial.
- Alternative considered: try refresh first for any 403, falling back to bootstrap only if refresh itself fails. Rejected — for `csrf_failed`, refresh is not merely useless, it is *itself blocked* by the same missing cookie (`POST /auth/refresh` is a state-changing request behind the same middleware), so "try it first" spends a request and a round trip on a call that cannot succeed before falling through to the mechanism that actually helps.
- **Bounded composition.** A single originating request is retried at most once, by at most one of the two paths, ever. Nothing retries the retry: a bootstrap-recovered request that still fails does not then attempt a refresh, and a refresh-recovered request that still fails does not then attempt a bootstrap. Without this bound, a request failing for a reason neither path fixes — a genuine permission denial arriving as `forbidden` right after a refresh already ran, say — could otherwise cycle between the two recoveries indefinitely.
- **Bootstrap is single-flight for stampede avoidance, not for the destructive reason refresh is.** Concurrent callers share one in-flight bootstrap call the same way they share one in-flight refresh, but the stakes differ: a duplicated refresh revokes the entire session lineage (see above); a duplicated bootstrap merely re-issues the same cookie twice, wasteful but harmless. The same pattern is applied here for a lower-stakes reason, not because bootstrap has the same failure mode refresh does.
- **A throttled bootstrap call is indistinguishable from a legitimate one that found no session, on purpose — and that has a client-side cost.** The endpoint's response is uniform 204 in both cases (`specs/authentication` - "Authentication attempts are rate limited"), so the interceptor cannot tell "you are rate limited, try later" from "no session exists here." A caller throttled mid-recovery gets exactly one retry, per the bound above, sees it still fail, and lands on the same generic failure or sign-in path as a caller who was never going to recover at all. Accepted: the alternative is a distinguishable throttled response, which is precisely the oracle the uniform-204 design exists to prevent, and the rate limit's window is short enough that the next ordinary request — not a special retry — succeeds once the window clears.

**Deep-link preservation is client-side and relative-path-only, independent of `resolveRedirectTarget`.** `resolveRedirectTarget` (`apps/api/src/lib/redirect.ts`) validates a post-sign-in target against an origin allowlist, but it is server-side and wired only into the Google OAuth callback; staff sign-in returns 204 with no redirect field at all. The admin app therefore captures the originally requested route itself (e.g. before redirecting an unauthenticated visitor to `/login`) and restores it after a successful sign-in, accepting the target only if it is a same-app relative path. The restriction exists for the same reason `resolveRedirectTarget` has one: an unvalidated redirect target on a route the caller just authenticated through is a phishing vector, and that risk doesn't go away just because this path is client-side instead of server-side.
- Alternative considered: extend `POST /auth/staff/login` to accept and validate a `next` parameter server-side, mirroring the Google flow. Rejected — the endpoint has no redirect semantics today (it returns 204), and adding one is exactly the kind of endpoint redesign this change avoids; the client already has everything it needs to make this decision itself.

**Generic sign-in failure UI: render the server's response, and stop there.** `specs/authentication` already makes the server's failure response indistinguishable for a wrong password, an unknown email, and a throttled attempt (`respondWithGenericFailure`, `auth.routes.ts:24-26`, always 401 `invalid_credentials`). The client's job is to not undo that: the sign-in screen shows one fixed message for any rejected attempt and never branches on the error's `code` to synthesize a "too many attempts" state the server didn't send.

**The reader/staff shared CSRF cookie stays shared; this remains safe under the fix above.** `app.sessions` rows are partitioned by `subjectType`, and `resolveReaderAccess`/`resolveStaffAccess` (`authorize.ts:71-85`, `:136-161`) each query only their own subject type — a CSRF token's binding is to a `sessionId`, not to a subject type, and that `sessionId` was already exclusively a reader's or a staff member's before this change. Giving the cookie a longer lifetime doesn't change which sessions it can be used against; it only changes how long the token stays paired with whichever refresh cookie it was issued alongside. The two subject types remain mutually exclusive by construction, so nothing here is a new namespace-collision risk — it is an accepted constraint carried forward unchanged, not a new one introduced by this change.

## Risks / Trade-offs

- **[Sign-out is not a cryptographic guarantee on a failed network call]** → httpOnly cookies can only be cleared by a successful server response (`clearSessionCookies`/`clearCsrfCookie`); if the `POST /auth/logout` call itself fails (e.g. offline), the client-visible "returned to sign-in" is a rendering decision, not proof the session ended server-side. Accepted: the real control is the successful call, and a caller who is offline can't reach any other endpoint either.
- **[CSRF cookie now persists up to 30 days on a shared device]** → the fix deliberately extends a script-readable cookie's lifetime to match `sid_rt`, which already persists that long. Accepted as no new exposure: the CSRF cookie alone authorizes nothing without the httpOnly session cookie it is paired with, and `sid_rt`'s own 30-day window is unchanged by this proposal (see Non-Goals).
- **[Boot probe adds one request to every cold load]** → `GET /users/me` runs before any protected route renders. Accepted — it is the same cheap, already-indexed call `getMe` serves today, and every session-aware SPA pays an equivalent cost.
- **[The refresh → retry → re-probe chain adds latency to a genuine permission denial]** → up to three sequential requests before a denial renders. Accepted deliberately: this path is only reached when a refresh didn't resolve the first 403, which is the uncommon case, and correctly separating "no permission" from "no session" matters more here than shaving one request off it.
- **[Reported `permissionKeys`/`isOwner` can lag the caller's true state between probes]** → rendered navigation can be briefly stale until the next `/users/me` read (e.g. the next refresh cycle or an explicit re-probe). Mitigated structurally, not by freshness: `admin-session`'s "Permission-aware rendering is cosmetic" requirement means staleness here is a rendering nuisance, never a security gap, because the server re-evaluates every request regardless of what was last reported.
- **[Sibling subdomain can already read `csrf_token`]** → `csrf_token` is `httpOnly: false` on `domain: COOKIE_DOMAIN`, so any subdomain sharing that cookie domain could already read it before this change. Accepted as pre-existing and out of scope: the CSRF bootstrap endpoint does not introduce or worsen this — it issues the same shape of cookie every other issuance point already does — and closing it would be a change to the cookie domain strategy, not to this endpoint.

## Build Order

1. **Backend fixes first** — CSRF cookie `maxAge`, the new `GET /auth/csrf` re-pairing endpoint, and the `permissionKeys`/`isOwner` DTO fields. All three are additive and independently shippable ahead of any frontend work; the frontend's CSRF recovery and permission-aware rendering have nothing to call or consume without the second and third.
2. **Session API client** — the module wrapping the now-six endpoints, built on the existing `apiFetch`/`apiUpload`.
3. **Interceptor: code-based branching, single-flight refresh, single-flight bootstrap** — everything else that talks to a feature route depends on this existing first, including the boot probe itself (Goal: boot-time 403s recover the same way mid-session ones do) and the sign-in screen (Goal: a caller already locked out can still reach it).
4. **Route guard + boot probe**, then **sign-in screen** with generic failure handling, then **forced password-change screen**, then **logout**, then **deep-link preservation**, then **permission-aware rendering** — each consumes the layer below it and is otherwise independent.

## Migration Plan

No schema change. The CSRF cookie `maxAge` change and the new `GET /auth/csrf` endpoint are backward-compatible additions; the `GET /users/me` change is a backward-compatible additive field on an existing response body. Rollback is reverting the `maxAge` addition, removing the new endpoint, and reverting the two new DTO fields — none has any data to backfill in either direction.

**The `maxAge` fix and the bootstrap endpoint address two different populations and neither substitutes for the other.** The `maxAge` fix is prospective: deployed alone, it prevents any *new* browser from ever reaching the lockout state, but a staff member whose browser already holds `sid_rt` with no `csrf_token` — anyone who hit this before the fix shipped — stays locked out until `sid_rt` itself expires (up to 30 days) or they clear cookies by hand; the fix changes nothing about a cookie that was already set without a `maxAge`. The bootstrap endpoint is what actually recovers that population, and is why both ship together rather than the `maxAge` change alone being treated as sufficient. No explicit backfill or notification is planned: the next time an affected staff member's browser attempts any admin request, the client's reactive `csrf_failed` → bootstrap → retry path (see `specs/admin-session`) repairs it without operator involvement.
