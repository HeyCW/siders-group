## ADDED Requirements

### Requirement: Persistence engine

The system SHALL use MySQL 8.0 as its relational database engine for all application data. No
component SHALL depend on a PostgreSQL-specific SQL feature (native `RETURNING`, `LOCK TABLE`,
partial indexes, Row Level Security, or a non-default schema namespace).

#### Scenario: Fresh environment provisioning

- **WHEN** a new environment is provisioned from the schema and migrations in `packages/db` and
  `db/migrations`
- **THEN** it succeeds against a MySQL 8.0 server with no manual intervention and without
  connecting to any Postgres server

#### Scenario: No Postgres-only syntax remains

- **WHEN** the schema, migrations, and repository query code are inspected
- **THEN** no `RETURNING` clause, `LOCK TABLE` statement, partial (`WHERE`-qualified) index, or
  Row Level Security policy is present

### Requirement: Application-generated primary keys

Every table's primary key SHALL be generated by the application before the row is written, not
by the database. Generated identifiers SHALL be time-ordered (UUIDv7 or equivalent) so that
sequential inserts append to, rather than fragment, the primary key's storage order.

#### Scenario: Identifier known before insert

- **WHEN** a repository constructs a new row for any table
- **THEN** the row's primary key value is already determined by the application prior to issuing
  the `INSERT` statement

#### Scenario: Sequential inserts sort adjacently

- **WHEN** two rows are inserted into the same table in immediate succession
- **THEN** the second row's identifier sorts after the first row's identifier under plain
  lexicographic comparison

### Requirement: Write operations return the persisted row via a transactional read

Any repository operation that reports the state of a row it just wrote (insert or update) SHALL
obtain that state by reading the row back inside the same transaction as the write, rather than
relying on the write statement itself to return it. The reported state SHALL reflect exactly what
was persisted, including any database-computed defaults.

#### Scenario: Insert reports persisted defaults

- **WHEN** a repository inserts a row that relies on a column default (for example a timestamp
  default) and reports the created row to its caller
- **THEN** the reported row's default-derived fields match what was actually written to storage,
  not a value computed only in application memory

#### Scenario: Update reports the row after the write lands

- **WHEN** a repository updates a row and reports the updated row to its caller
- **THEN** the reported row is read after the update statement has been applied within the same
  transaction, and a concurrent unrelated transaction cannot observe the reported state before
  the transaction commits

### Requirement: Reorder operations are mutually exclusive per orderable collection

Operations that replace the ordering of a set of rows (guide picks, partners, and any other
orderable collection using the shared reordering helper) SHALL be serialized so that at most one
reorder for a given collection is in flight at a time, for the full duration of that collection's
read-modify-write sequence. A reorder that cannot obtain exclusivity within its timeout SHALL be
rejected rather than proceeding against a potentially stale read of the collection.

#### Scenario: Concurrent reorders on the same collection

- **WHEN** two reorder requests for the same orderable collection are issued concurrently
- **THEN** one completes and the other either waits and then observes the first's result, or is
  rejected as a conflict — in no case do both complete and leave the collection in an order that
  reflects only part of one request

#### Scenario: Reorders on different collections do not block each other

- **WHEN** a reorder request for one orderable collection is in flight
- **THEN** a concurrent reorder request for a different orderable collection is not blocked by it

#### Scenario: Lock acquisition failure is a rejection, not a silent proceed

- **WHEN** a reorder request cannot obtain exclusivity on its collection within the configured
  timeout
- **THEN** the request is rejected with a conflict error and no ordering change is written

### Requirement: Constraint violations are classified independent of driver representation

The system SHALL classify a write failure as a unique-constraint violation or a foreign-key
violation based on a stable, driver-independent check, and SHALL be able to identify which named
constraint was violated when a single statement could violate more than one constraint of the
same class.

#### Scenario: Unique violation is classified correctly

- **WHEN** an insert or update violates a unique constraint
- **THEN** the system reports it as a unique-constraint violation and can report which
  constraint was violated

#### Scenario: Foreign-key violation is classified correctly in both directions

- **WHEN** an insert or update violates a foreign-key constraint by referencing a missing row, or
  a delete violates a foreign-key constraint by leaving a dependent row orphaned
- **THEN** the system reports both cases as a foreign-key violation

#### Scenario: Ambiguous unique violation resolves to the actual constraint

- **WHEN** a single write statement could violate either of two distinct unique constraints on
  the same table
- **THEN** the system's classification names the constraint that actually fired, not the other
  one

### Requirement: Timestamp precision supports keyset pagination without collision

Every stored timestamp used as part of a sort or pagination cursor SHALL be recorded with at
least millisecond precision, and all timestamps SHALL be interpreted in UTC regardless of the
originating connection's local session settings.

#### Scenario: Two events in the same second remain orderable

- **WHEN** two rows that participate in a keyset-paginated listing are created within the same
  second
- **THEN** their stored timestamps are distinguishable enough, combined with their identifiers, to
  produce a stable total order with no row skipped or duplicated across a page boundary

#### Scenario: Timestamps are stored and compared in UTC

- **WHEN** a row is written from a connection or process running in a non-UTC local time zone
- **THEN** the stored timestamp value is equivalent to what would have been stored from a UTC
  connection for the same instant

### Requirement: The application database credential holds only data-manipulation privileges

The database credential used by the running API SHALL NOT be able to alter schema (create, alter,
or drop tables, indexes, or other schema objects). Schema changes (including running migrations)
SHALL be performed under a separate credential not used by the running API.

#### Scenario: API credential cannot alter schema

- **WHEN** the API's database credential is used to attempt a schema-altering statement
- **THEN** the database rejects it as a privilege violation

#### Scenario: API credential can perform ordinary reads and writes

- **WHEN** the API's database credential is used to select, insert, update, or delete rows within
  the application's tables
- **THEN** the operation succeeds, subject to the same constraints any other credential with
  those privileges would observe
