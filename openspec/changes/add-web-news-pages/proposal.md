## Why

`apps/web` is still four literal stub pages (`<main>Siders</main>`, `<main>News</main>`, `<main>Article: {slug}</main>`) even though the backend it should render is real and archived: `public-news-api` (article list + by-slug), `home-curation` (the composed `/home` feed), `reels-curation` (the public `/reels` rail), and `category-management` (the public `/categories` list) all exist and are implemented on `main`. Four separate archived changes (`add-home-curation`, `add-reels-curation`, `add-news-management-system`, `add-admin-dashboard`) each deferred rendering `apps/web` to a follow-up they name explicitly as `add-web-news-pages` — this is that change.

`docs/ARCHITECTURE.md` §8.1 already specifies the four routes this change ships (`/`, `/news`, `/news/[slug]`, `/contact`) and their rendering strategy. This change satisfies that table rather than redesigning it.

Separately, a full visual design for these same four pages — masthead, News filters, Article layout, Contact, footer — was produced in Claude Design (`Siders Broadsheet.dc.html`, handoff bundle at `/home/claude/repo`) and reviewed with the user. That prototype is HTML/CSS/JS using a design-tool-specific templating syntax (`x-dc`, `sc-for`, `sc-if`) with placeholder/sample content — not React, and not wired to anything real. This change recreates its visual system pixel-for-pixel as componentized React/Tailwind, and wires it to the real backend wherever the backend has the capability the design assumes.

It does not always have that capability. See **Non-Goals** — this proposal was written after auditing `packages/contracts`, `apps/api/src/modules/*`, and `packages/db/src/schema/*` against what the prototype's News filters, Article engagement bar, and Contact form assume, and several assumed capabilities (sub-brand filtering, search, comments, likes, contact submission) do not exist in this codebase today, in any form.

## What Changes

- Add Tailwind CSS to `apps/web` (currently has none), matching `CLAUDE.md`'s stated stack and `apps/admin`'s existing Tailwind setup. Plain Tailwind utilities, no `shadcn/ui` — `apps/admin` doesn't actually use shadcn either (no `components.json`, no Radix/`cva`/`clsx` dependency anywhere in the repo despite `CLAUDE.md` naming it), and the design's exact-hex, exact-rule-weight editorial system is expressed more directly in utilities/tokens than in shadcn's component primitives.
- Add `apps/web`'s API client: a thin `fetch` wrapper against `NEXT_PUBLIC_API_URL`, typed with `@siders/contracts` response schemas, following the error-envelope convention (`{ success, data }` / `{ success: false, error: { code, message } }`) every other client in this repo already follows. Public reads only — no session/CSRF handling, since every endpoint this change calls is `requirePublic()`.
- Add a shared layout: sticky masthead nav (SIDERS wordmark + Home/News/Contact), the rule-line masthead header, and a footer (wordmark + one-line description, page links, Anak Usaha sub-brand links, redaksi contact block, colophon row).
- Implement `/` (ISR, 60s + on-demand revalidate, per `docs/ARCHITECTURE.md` §8.1): hero manifesto copy, three-column intro blurb, stats band, "Siders Guide of the Week," the "SidersVox — News & Community" showcase and Reels rail wired to `GET /home` and `GET /reels`, the Anak Usaha tile row, the partner grid, and the closing CTA band.
- Implement `/news` (server-rendered, searchParams-driven, per `docs/ARCHITECTURE.md` §8.1 — "filters live in the URL, so results are shareable"): search-styled input (client-side substring match over the loaded page — see Non-Goals), a working category filter backed by `GET /categories` + `GET /articles?categorySlug=`, active-filter chip, result count, featured article, article grid, empty state, and load-more via `limit`/`offset`.
- Implement `/news/[slug]` (SSG + on-demand revalidate, per `docs/ARCHITECTURE.md` §8.1): kicker/title/byline, lead image, drop-cap body from `bodyHtml`, and a related-articles rail from `GET /articles?categorySlug=<shared category>&excludeIds=<current>`.
- Implement `/contact` (static, per `docs/ARCHITECTURE.md` §8.1): get-in-touch info blocks, sub-brand follow links, a form (client-side validation only — see Non-Goals), and a map image slot.
- **BREAKING**: none. `apps/web` had no real behavior to break.

## Non-Goals

Each item below is a capability the prototype's markup assumes that this audit found **does not exist anywhere in this codebase** — not in `packages/contracts`, not in `packages/db/src/schema`, not as an `apps/api` module or route. Building real UI against a capability that doesn't exist would mean inventing parallel mock data, which the user explicitly asked this change not to do. Instead:

- **Sub-brand ("Anak usaha") as a queryable concept.** There is no `subBrand`/`property` field anywhere — not on `Article`, not as its own entity. The prototype's Anak usaha filter pill, its four-tile home section, and its footer links all reference SidersVox / Surabaya Siders / Jakarta Siders / Siders Culture. This change renders those four names as **static content** (footer links point at `/news`, since there is nothing narrower to link to yet; the home tiles and the News filter pill are visual chrome with no working filter behind them — see `design.md` for exactly how each is handled). Filtering by sub-brand is a backend change, not shipped here.
- **Full-text search.** `articlePublicListQuerySchema` has no query-text parameter. The News search input performs a client-side substring match over whatever page of articles is currently loaded — real filtering of real data, but not a search across the whole archive. Flagged in the UI copy as "search this page," not "search stories."
- **Multi-select category filtering, date-range filtering, and sort.** The public list endpoint accepts exactly one `categorySlug` and always orders newest-first. The News page's Kategori filter is implemented as **single-select** against real category data (a real, if narrower, capability than the design draws). Tanggal (date range) and Urutkan (sort) render as visual chrome with no effect — same treatment as Anak usaha, and for the same reason.
- **Comments, likes, and share counts.** `docs/ARCHITECTURE.md` §8.1/§9.1/§9.3 anticipate a reader-engagement system (a `readers` table exists; comment/like rate-limit buckets are named in prose) — but no comments table, no likes table, and no `apps/api` module for either exists yet. This is a materially different situation from the static content above: the prototype's "55 Comments," "960 Shares," and named sample commenters are fabricated activity, and hardcoding them into shipped code would misrepresent real user activity in a way a static footer address does not. The Article page ships the engagement bar's visual structure with **no counts and no working submission** — like/comment/share affordances are present but inert, each with a one-line comment in the code pointing at this Non-Goal. A follow-up change (comments/likes backend) is required before this bar can be real.
- **Contact form submission.** No endpoint accepts a contact submission (§9.3 names a `contact` rate-limit bucket in prose; nothing implements it). The form validates client-side and shows a "sending isn't wired up yet" state on submit rather than silently pretending to succeed or POSTing somewhere that doesn't exist.
- **"Siders Guide of the Week" as data.** The prototype's Surabaya/Jakarta guide cards (place name, city, one-line description, photo) don't fit the `Article` shape (no place/city fields) and there's no separate "guide" entity. Shipped as static editorial content — the same category of content as the manifesto copy and the stats band, authored directly in the component, not fetched.
- **Partner/sponsor logos.** No sponsor entity exists. Shipped as a static list of names in the placeholder tile style the prototype itself used before real marks were supplied (per `chats/chat1.md`: "sub-brand and partner marks are placeholder tiles until you supply SVGs").
- **Traffic/stat numbers (500+ brands, 450+ people, 100.000.000+ views).** Editorial marketing copy, not a live metric — `apps/api/src/modules/analytics` is an admin-only surface with no public traffic endpoint (view-counting itself is unbuilt per `add-admin-dashboard/proposal.md` — "No traffic/view-counting pipeline"). Static text.
- **Image slots.** `image-slot.js`/`support.js` are Claude Design's own editor tooling (drag-and-drop image placement inside the design tool) and have no equivalent in a shipped site. Every `<image-slot>` in the prototype becomes an `<img>`/`next/image` with a stored placeholder asset, swappable later through ordinary media upload — no new "slot" abstraction is introduced.

## Capabilities

### New Capabilities

- `web-public-site`: the public site's rendering behavior across `/`, `/news`, `/news/[slug]`, and `/contact` — what each route fetches, how it composes the visual system, its filter/search/pagination behavior on `/news`, and which prototype-implied capabilities it deliberately does not wire up (this proposal's Non-Goals).

### Modified Capabilities

_None._ `public-news-api`, `home-curation`, `reels-curation`, and `category-management` are all consumed as-is; no delta is recorded against any of them. This change is a pure consumer.

## Impact

- **Affected code**: `apps/web/app/**` (all four route files, replacing their stubs), new `apps/web/components/**` (shared layout + per-page pieces), new `apps/web/lib/api.ts` (public fetch client) and `apps/web/lib/*` (types re-exported from `@siders/contracts`), `apps/web/package.json` (add `@siders/contracts`, `tailwindcss`, `postcss`, `autoprefixer`), new `apps/web/tailwind.config.ts` + `apps/web/app/globals.css`, `apps/web/next.config.mjs` (no change needed beyond its existing comment, which this change fulfills).
- **Dependencies**: this change is a pure consumer of `public-news-api`, `home-curation`, `reels-curation`, and `category-management`, all implemented and archived on `main`. No migration, no new backend module, no contract change.
- **Environment**: `NEXT_PUBLIC_API_URL` (already documented in `docs/ARCHITECTURE.md` §10) must be set for `apps/web` to reach `apps/api`; `env.APP_ORIGIN` on the API side (already read by `apps/api/src/server.ts`'s CORS config) must match `apps/web`'s deployed origin. Neither is a code change here, both are already anticipated.
- **Docs**: none required — this change satisfies `docs/ARCHITECTURE.md` §8.1 rather than altering it. If a follow-up ships sub-brand filtering, search, or comments/likes, that follow-up should update this capability's spec rather than this one being revisited.
